# Spec Delta

## Purpose

规范 Dots 网站向公开 GitHub 仓库交接反馈的方式，使访客能够区分问题报告、形象需求与一般建议，并提交维护者可以理解和处理的信息，同时保持网站的静态角色库能力与角色批准流程清楚独立。

## ADDED Requirements

### Requirement: 网站反馈必须明确交接到 GitHub
网站 SHALL 将源码入口指向 `https://github.com/liuzhihang/dots`，将反馈入口指向 `https://github.com/liuzhihang/dots/issues/new/choose`；两者 MUST 使用 HTTPS 并在新标签页打开，不改变原标签页的查询、排序、滚动和历史。网站 SHALL 提示反馈通过 GitHub 提交、需要登录且内容公开，并提供可感知的新标签页说明。网站 MUST NOT 自动创建 Issue、上传附件、携带 Prompt 或收集网站账号信息。

#### Scenario: 从带筛选的图库进入反馈
- **WHEN** 用户搜索、筛选、排序并滚动后打开反馈入口
- **THEN** 新标签页访问仓库的反馈分类选择地址；原标签页保留相同 URL、查询、排序与滚动位置，不新增站内历史记录或清空状态

#### Scenario: 未登录或 GitHub 无法访问
- **WHEN** 用户未登录 GitHub，或外部目标无法访问
- **THEN** 登录及网络结果由 GitHub 和浏览器处理，原图库仍可使用；网站不宣称反馈已提交，不要求提供 GitHub 凭据，也不替用户提交

### Requirement: GitHub 必须提供三个清楚的反馈类别
公开仓库的 Issue 选择器 SHALL 提供“问题反馈 / Bug report”“申请新增形象 / Character request”“功能与体验建议 / Suggestion”三个表单，每个表单使用中英同列的名称、说明和字段标签。选择器 SHALL 引导普通贡献者使用这三个类别且不展示空白 Issue 选项；维护者保留 GitHub 自身允许的空白 Issue 能力。这是选择器配置，不是对 API 或其他创建方式的访问限制。网站语言切换 MUST NOT 产生另一套模板或声称能控制 GitHub 的界面语言。

#### Scenario: 选择反馈类型
- **WHEN** 用户访问已生效的反馈选择器
- **THEN** 能辨认并选择三个类别；每个类别有说明且打开对应表单，没有仅因网站语言不同而出现的六个重复模板

#### Scenario: 普通贡献者与维护者访问
- **WHEN** 普通贡献者或有写权限的维护者打开选择器
- **THEN** 普通贡献者只见三个配置类别；维护者的空白入口遵循 GitHub 权限规则，不被网站误称为配置失败

### Requirement: 问题表单必须收集可复现信息
问题反馈表单 SHALL 必填实际表现、预期表现和复现步骤，提供受影响角色或页面链接、浏览器/系统/设备、截图或录屏的选填字段。表单 MUST NOT 要求访客填写提交 SHA、内部资源 hash、开发者日志或额外联系方式才能提交。附件 MUST 保持选填，并提示只提供可公开的信息。

#### Scenario: 提交最小问题描述
- **WHEN** 用户填写实际表现、预期表现和复现步骤，但未提供环境或附件
- **THEN** 表单允许继续由用户提交；缺少任一必填信息时明确标识该字段，填写后可继续

### Requirement: 形象表单必须收集需求而非授予批准
形象申请表单 SHALL 必填写明想要的形象和关键外观特征；配色、服装或配饰、用途及参考链接或图片为选填。表单 MUST 明示提交为建议、不保证制作或采纳，且参考素材应可公开分享；MUST NOT 将 Issue、附件或点赞视为 Artwork/Template 获批、素材已授权、自动生成结果或角色已加入图库。

#### Scenario: 提交没有参考图的形象申请
- **WHEN** 用户描述想要的形象及外观特征，但没有参考图片
- **THEN** 表单允许继续由用户提交，不要求选定现有家族、提供图片或承诺本地编辑当前不支持的能力

#### Scenario: 用户附上参考素材
- **WHEN** 用户自行向 GitHub 添加可公开分享的参考链接或图片
- **THEN** 它仅作为该 Issue 的需求资料，不由网站读取或自动进入角色目录、发布闭包及批准记录

### Requirement: 一般建议表单必须保持轻量
功能与体验建议表单 SHALL 必填当前问题或改进机会及期望结果，提供建议类别、相关页面和截图作为选填。建议类别 SHALL 包含功能、视觉、易用性与其他，允许不选类别也能提交完整描述。表单 MUST NOT 将建议表述为既定路线图或要求用户上传附件。

#### Scenario: 提交一般体验建议
- **WHEN** 用户说明当前体验问题和希望的改进，但未选择类别或附图
- **THEN** 表单允许继续由用户提交，描述保留在所选建议类别的 Issue 中

### Requirement: 表单生效必须以远端默认分支结果为准
表单及选择器配置 SHALL 由仓库默认分支提供。仅存在本地文件或本地校验通过时 MUST NOT 宣称模板已上线；远端验收 SHALL 能打开三个类别及其表单，确认必填、选填与可选附件，不自动提交测试 Issue。模板上线和网站上线 SHALL 分别记录各自状态。

#### Scenario: 本地实现完成但未发布
- **WHEN** 三个表单文件已在本地完成并通过结构校验，但尚未进入远端默认分支
- **THEN** 只报告本地已完成、远端未生效；不把本地结构结果当作 GitHub 实际表单验收

#### Scenario: 获授权后验收远端模板
- **WHEN** 模板经独立授权进入远端默认分支并执行只读页面验收
- **THEN** 核对三个表单及选择器的真实状态并停在提交之前；Site 是否已提供入口单独报告
