# Design

## Context

请参阅[提案](proposal.md)了解动机，并参阅[规范](specs/)了解用户可见要求。项目是通过 `dist/` 提供的原生 HTML/CSS/JavaScript 单页应用，使用 Vite 进行本地预览，由现有 `studio.js` 负责状态管理，并将创作与组合模块分开。v30 已有 R01 首页与工作台，但封面和家族卡各只呈现一只代表，创作入口重复，工作台还保留技术模式标签。已确认的 [R01 参考图](../rebuild-character-system/references/r01-confirmed-direction.jpg)展示了亲切的主视觉、五张柔和色调的家族卡片，以及紧凑的创作介绍区。图中的登录和“我的空间”控件不属于产品范围。用户最新确认后，本次更新将路径扩展为封面、内置形象画廊与创作工作台；首版布局与已完成 QA 仍是历史交付事实，不作为新路径已完成的证明。

应用已经支持 Artwork、Composer、Prompt、项目 JSON、参考图 Prompt 模式和打开 ChatGPT。当前各组素材和组合包的可用情况并不一致。视觉刷新必须如实呈现实际可用能力，并让每组唯一的基准候选与已验收美术作品清楚区分。

## Goals / Non-Goals

**目标：**

- 调整首屏内容顺序，使产品用途、五个家族和开始创作的路径一目了然。
- 在封面呈现各家族群像，并提供独立的内置形象画廊与创作工作台入口，避免重复 CTA。
- 将 R01 明亮的柔和色面、醒目的深色字体、宽松布局、精心呈现的角色素材和克制的控件风格延伸到编辑器。
- 保留五个家族名称及各自的身份特征；每组保留一只 canonical 基准，并把本轮 gallery 规划限定为另外两项候选。
- 将现有形象、Prompt、项目和真实组合操作组织成易于理解的创作路径。
- 调整呈现方式和浏览器交互时，保留当前项目状态与兼容性。

**非目标：**

- 不重建站点，不引入新框架、素材生成后端、认证、账号、云端作品库或上传服务。
- 不在本 change 中实现家族导航状态转换或沉浸式随机流程状态机；这些分别由 `refactor-family-navigation` 和 `add-fullscreen-randomizer` 负责。
- 不把生成概念图、构建成功、静态示例或任务完成视为角色通过美术验收。
- 不更改角色配置 schema 或 Artwork/Composer 输出合同。

## Decisions

### 将现有应用组织成封面、画廊与工作台

在现有单页应用中协调封面、内置形象画廊与创作工作台。封面遵循 R01，包含简洁顶栏、柔和色调的主视觉、9–12 个单独登记角色素材构成的群像和五张家族卡；MUST NOT 将全屏效果图用作产品内容。家族卡和封面主 CTA 通向“内置形象”画廊，进入后默认筛选相应家族并查看该组三只已装配形象。顶层入口分别为“内置形象”和“创作工作台”。单张形象卡只用一个“用这个形象定制”动作把当前素材/配置带进工作台，不再以两个同义 CTA 指向同一处。工作台承载编辑、真实预览、Prompt、背景与输出能力，并保留当前家族和项目状态。该决策取代首版的两状态路由与单只主视觉方案；首版实现与检查记录仍作为已完成的历史事实。

**备选方案：**将主页面做成长篇着陆页，只把旧编辑器推到首屏以下。不采用此方案，因为用户明确区分现成形象浏览和定制两种目的，也需要封面、画廊和工作台间清楚的路径。

### 重组现有模块，而不替换状态管理方

继续由 `studio.js` 负责当前项目、选择状态和渲染生命周期。在页面外壳中调整或包裹现有应用区域，并用小型展示组件和样式呈现主视觉、家族概览、创作步骤与工作台。现有创作和导出操作应继续调用当前应用处理程序。刷新后的实现不得将设置拆分到独立的着陆页状态，也不得在用户进入工作台时悄悄重置当前项目。

**备选方案：**另建一个独立着陆页应用，再通过路由挂载编辑器。不采用此方案，因为项目是静态单页应用，重复维护导航和状态会导致两个界面对当前家族和项目的认知不一致。

### 由独立变更负责家族导航与随机行为

本 change 为五张家族卡片和顶层家族标签设计视觉结构。它们的选中状态、搜索、筛选、选择保留及移动端导航行为由 `refactor-family-navigation` 规定。主视觉中的随机按钮由 `add-fullscreen-randomizer` 提供最终流程。在这些变更集成前，视觉元素只能连接到已经实现的处理程序，不得另行设计一套随机状态机。

**备选方案：**在本视觉变更中实现全部卡片、筛选和随机状态。不采用此方案，因为用户明确要求分别管理这些变更，而且它们的状态行为有各自独立的验收要求。

### 区分界面素材与美术验收证据

本轮内置形象范围按每组一只 canonical 基准加两只画廊候选规划。候选标签、来源和输出能力在画廊与工作台中保持可见。家族素材必须来自本项目的素材工作；不得把生成的网站效果图作为整页内容插入。人物与动物图片必须重新设计，不得使用动漫截图像素、裁切素材或可识别的完整角色复刻。Dots、Grok Bot 和 Meta Muse 可以保留获得许可的软件身份，并注明来源。R01 的画面构图不代表任何实际候选已获批准。

**备选方案：**将整张 R01 截图用作背景，或用静态效果图替代产品页面区域。不采用此方案，因为页面必须保持可交互，设计图中的角色也不是已渲染、可编辑且通过验收的产品素材。

### 将内置形象画廊与定制工作台分开呈现

内置形象页的本轮实现范围设为五组各三只完整角色，共 15 项：每组现有 canonical 基准一只，加两项 gallery-only 候选。此数量是对用户丰富家族展示要求的有界实现选择，不是用户指定的数字。图库负责浏览、搜索/筛选、查看来源、原图下载和读取对应 Prompt；使用“用这个形象定制”将所选完整形象带入工作台。动物和人物新形象须重新设计，不可从动漫截图直接取图或照搬完整角色。所有图库作品均标记真实的候选状态。

工作台是一个单一、连续的定制界面，不向用户显示 Artwork / Composer 技术模式页签。既有 Artwork、Composer、结构诊断、Prompt、项目 JSON 和版本 10 配置仍按 `rebuild-character-system` 底层合同运行。全体五组的可视输出均由受信任登记的完整姿态模板、明确列出的变体和可用背景实际绘制到 Canvas；角色形状、配饰或动作只有在完整模板/受信任配方登记时才改变输出。其它设定可保留在 Prompt 和 JSON 中，但要明确说明不会改变当前 Canvas。用户可直接编辑不意味着本站有任意 3D、任意姿态或未登记配饰生成能力。

在该图库限定范围中，每组新增两项候选是本 change 为实现丰富家族展示而选定的一次性范围。它们不会替代该组唯一 canonical 基准，也不会通过图库展示、原图下载、Prompt 或程序 Canvas 而成为美术已验收。该组后续形象扩展仍须等该组基准完成真实网页验收并得到用户明确确认；不得把本轮范围变成无限增量许可。

### 以五家族完整姿态模板实现受限的真实 Canvas 工作台

2026-10-05 v30 早期交付只给 Dots 单只基准提供裸形/耳机两种互斥的真实 Canvas 配方；其余四组只保留 Prompt 与项目配置。该限制是当时发布事实。为回应用户最新提出的五组形象画廊和创作工作台要求，本 change 规划为五组分别接入已登记的完整姿态模板、显式变体和实际 Canvas 背景合成；保留 Dots 裸形/耳机配方。其它可选形状和配饰必须对应真实完整资产，不能叠加两张不同身体形状的图片，也不得把共享 Prompt 控件误标为可视输出。每组支持参数由可审计清单逐项声明。任何超出能力的设定继续保留在 Prompt/JSON，页面说明不会影响当前 Canvas。画廊候选及全部 Canvas 结果仍待验收，不以成功渲染 PNG 代表美术通过。

**备选方案：**等五个家族的组合包全部完成后再开放工作台。不采用此方案，因为最新用户要求把工作台作为五组共同的定制入口；按每个实际受信任模板的能力渐进开放，未登记设置始终不宣称生成。

### 在窄屏采用流动布局并保持清晰的创作顺序

沿用现有 CSS 架构，明确区分宽屏、平板和窄屏布局。在窄屏下，按阅读顺序纵向排列主视觉、家族卡片和创作工作台；无需横向滚动即可看到主要创作操作。必要时可以将编辑器面板改为纵向排列或折叠，但预览及其真实状态标签必须易于找到。遵循键盘焦点和减少动态效果偏好。

**备选方案：**将桌面双栏检查器直接缩小到手机宽度。不采用此方案，因为它会把角色预览和控件挤压到无法使用的首屏中。

## Risks / Trade-offs

- [R01 包含登录和个人空间入口] → 移除这些控件，只保留已经确认的布局与角色方向。
- [五张家族卡可能把封面主标题推到首屏以下] → 精简文案、明确群像与卡片的比例，封面提供单一“浏览内置形象”入口。
- [旧 v30 实现时只有 Dots 有受限 Composer，其余四组不可用] → 该限制是历史发布事实；本轮通过五组各自登记的完整姿态模板扩展为 Canvas，并在未登记设置上保留清楚的 Prompt-only 状态，不以其他家族资产填补缺口。
- [更改默认作品可能影响现有项目] → 导入旧项目 JSON 时继续解析历史素材 ID 和源文件；仅让新候选成为新建项目的默认素材。
- [视觉工作可能被误认为角色已获批准] → 单独记录界面视觉 QA；五组美术验收和用户确认状态均保持待处理，直到在真实页面上逐组评估。
- [展示候选被误认成通过验收的组内扩展] → 每组本轮最多规划两项新增图库候选；三项均展示候选状态，不自动开放其后的新增形象。
- [移除模式页签后用户误以为所有设置都渲染到 Canvas] → 工作台只展示清单登记的完整形象、变体与实际背景合成；未登记参数仅保留到 Prompt/项目，并显示不会改变当前画面的说明。
- [响应式样式可能遮挡现有编辑器控件] → 在桌面、768 px、390 px 和 320 px 真实页面中检查，确保导航、预览、状态和主要操作都能触达。

## Migration Plan

1. 围绕 R01 主视觉、家族概览和创作工作台重组现有页面外壳，同时保留当前项目与状态模块。
2. 两项独立变更准备就绪后，接入家族卡片交互和沉浸式随机入口；确保两项变更仍可分别审阅。
3. 为本轮规划的 15 项完整形象登记可信来源与模板范围，构建封面 9–12 人群像及每家族三项预览的形象画廊。以真实 Canvas 验证五组完整姿态形象和支持的背景合成、Dots 裸形/耳机配方、过期和未登记参数，以及画廊原图下载；确认旧项目 JSON 仍能恢复历史 `artworkId` 和撤下状态。真实浏览器检查家族筛选、搜索、画廊进入工作台、Prompt、复制/导入导出，并覆盖桌面、768 px、390 px、320 px。将页面/交互 QA 与逐组美术验收分别记录。
4. 对已获授权的源码发布和站点预览，通过现有私有仓库提交并推送本项目，且只向现有 Site 发布候选版本。回读已保存的版本和部署结果。保留 Site 当前访问策略；发布结果不代表任何角色美术已验收。
5. 如需回滚，恢复到最后一个已知良好的 Git 提交，并恢复同一 Site 上与之对应的先前已保存版本；始终保持项目 JSON 兼容。

## Open Questions

没有会改变视觉方向或要求的未决问题。素材可用性和每个候选的美术验收，均应依据完成后的真实页面评估，并作为各家族的独立决定保留。

## Feedback correction · 2026-10-05

只更新 HTML 入口 query 不会改变静态 import 的 URL。将入口、所有可达本地模块及 QA 入口中引用的同一模块统一为同一发布版本，防止旧角色目录与新首页混用；测试遍历真实模块依赖图，验证 Meta Muse 默认候选。

用户已明确拒绝的卷发阅读人物从可选素材及公开静态目录撤下，保存至非发布参考目录便于追溯。旧项目中的该 artworkId 保留为已撤下记录：恢复人物配置，但不给它另一张图，也不启用原图下载。此项是历史素材兼容的明确例外，其余历史作品仍保留原语义。

当时“把整图与组合并列展示为模式标签”及“每家族只展示一只形象”的方案已被用户最新反馈替代。用户当前已明确选择独立内置形象画廊与统一创作工作台的 IA。本 change 据丰富家族展示要求规划 15 项静态形象，并为工作台规划五组真实 Canvas 完整姿态模板与背景路径；这项数量决定由本 change 提出，不是用户逐字要求。该方向不等于已确认所有角色采用同一材质风格、扩展额外形象或支持任意三维捏形，也不改变 Artwork/Composer 的底层项目兼容及输出合同。

同轮用户追加 Grok 身份图：鲜明几何轮廓、双胶囊眼，包含圆形、云形、圆角方形、三角、水滴和六边形。唯一基准据图中 Cora 的紫色圆形制作，胶囊眼同向斜置、无嘴无肢体；配饰不是身份必备。新候选图使用内置 ImageGen 独立再现，来源明确为用户图片，不声明为官方原文件。新建基准与 Prompt 同步为紫球裸形；已有 JSON 中用户的形状、动作和配饰保持原值。旧浅绿眼镜笔电脑整图与已否决人物一样退役，不再作为 Grok 默认或可选图片。对 Grok，本 change 的 15 项范围规划可选圆形基准、绿色云形和青色圆角方形；三角、水滴、六边形及后续形状不在本次 15 项范围。
