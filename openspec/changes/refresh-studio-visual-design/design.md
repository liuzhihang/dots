# Design

## Context

请参阅[提案](proposal.md)了解动机，并参阅[规范](specs/)了解用户可见要求。项目是通过 `dist/` 提供的原生 HTML/CSS/JavaScript 单页应用，使用 Vite 进行本地预览，由现有 `studio.js` 负责状态管理，并将创作与组合模块分开。当前入口页以编辑器为主，包含大型预览、密集的检查器和底部配方机。已确认的 [R01 参考图](../rebuild-character-system/references/r01-confirmed-direction.jpg)展示了亲切的主视觉、五张柔和色调的家族卡片，以及紧凑的创作介绍区。图中的登录和“我的空间”控件不属于产品范围。本次刷新会在同一应用中协调 `home` 与 `workspace` 两种状态：首页介绍五个基准角色并直接导向编辑器，工作台则保留完整编辑界面。

应用已经支持 Artwork、Composer、Prompt、项目 JSON、参考图 Prompt 模式和打开 ChatGPT。当前各组素材和组合包的可用情况并不一致。视觉刷新必须如实呈现实际可用能力，并让每组唯一的基准候选与已验收美术作品清楚区分。

## Goals / Non-Goals

**目标：**

- 调整首屏内容顺序，使产品用途、五个家族和开始创作的路径一目了然。
- 将 R01 明亮的柔和色面、醒目的深色字体、宽松布局、精心呈现的角色素材和克制的控件风格延伸到编辑器。
- 保留五个家族名称及各自的身份特征，不增加家族或基准候选。
- 将现有形象、Prompt、项目和真实组合操作组织成易于理解的创作路径。
- 调整呈现方式和浏览器交互时，保留当前项目状态与兼容性。

**非目标：**

- 不重建站点，不引入新框架、素材生成后端、认证、账号、云端作品库或上传服务。
- 不在本 change 中实现家族导航状态转换或沉浸式随机流程状态机；这些分别由 `refactor-family-navigation` 和 `add-fullscreen-randomizer` 负责。
- 不把生成概念图、构建成功、静态示例或任务完成视为角色通过美术验收。
- 不更改角色配置 schema 或 Artwork/Composer 输出合同。

## Decisions

### 将现有应用重组为首页与工作台状态

在现有单页应用中实现相互协调的首页和工作台视图。首页遵循 R01，包含简洁的白色顶栏、柔和色调的主视觉、由五个独立透明素材组成的角色插画、五张家族卡片和清晰的开始创作入口；MUST NOT 将全屏效果图用作产品内容。工作台设有独立的顶层家族导航，保留五个编辑标签，并呈现当前预览和创作操作。开始创作后进入工作台，并保留所选家族和当前项目。布局借鉴 R01 的层级与氛围，但不照搬任何参考站点的界面。

**备选方案：**将主页面做成长篇着陆页，只把旧编辑器推到首屏以下。不采用此方案，因为用户需要明确的首页/工作台切换，而且编辑器需要容纳五个家族标签、模式、Prompt 和导出控件。

### 重组现有模块，而不替换状态管理方

继续由 `studio.js` 负责当前项目、选择状态和渲染生命周期。在页面外壳中调整或包裹现有应用区域，并用小型展示组件和样式呈现主视觉、家族概览、创作步骤与工作台。现有创作和导出操作应继续调用当前应用处理程序。刷新后的实现不得将设置拆分到独立的着陆页状态，也不得在用户进入工作台时悄悄重置当前项目。

**备选方案：**另建一个独立着陆页应用，再通过路由挂载编辑器。不采用此方案，因为项目是静态单页应用，重复维护导航和状态会导致两个界面对当前家族和项目的认知不一致。

### 由独立变更负责家族导航与随机行为

本 change 为五张家族卡片和顶层家族标签设计视觉结构。它们的选中状态、搜索、筛选、选择保留及移动端导航行为由 `refactor-family-navigation` 规定。主视觉中的随机按钮由 `add-fullscreen-randomizer` 提供最终流程。在这些变更集成前，视觉元素只能连接到已经实现的处理程序，不得另行设计一套随机状态机。

**备选方案：**在本视觉变更中实现全部卡片、筛选和随机状态。不采用此方案，因为用户明确要求分别管理这些变更，而且它们的状态行为有各自独立的验收要求。

### 区分界面素材与美术验收证据

每个家族有真实本地素材时，页面可以展示该组唯一的基准候选。候选标签、来源和输出能力在工作台中保持可见。家族素材必须来自本项目的素材工作；不得把生成的网站效果图作为整页美术内容插入。人物与动物图片必须重新设计，不得使用动漫截图像素、裁切素材或可识别的完整角色复刻。Dots、Grok Bot 和 Meta Muse 可以保留获得许可的软件身份，并注明来源。R01 的画面构图不代表任何实际候选已获批准。

**备选方案：**将整张 R01 截图用作背景，或用静态效果图替代产品页面区域。不采用此方案，因为页面必须保持可交互，设计图中的角色也不是已渲染、可编辑且通过验收的产品素材。

### 提供一条真实且有意受限的 Dots Composer 路径

首个 Composer 组合包使用同一只 Dots 基准，提供两种互斥的正面造型：裸主体，以及正确佩戴耳机的同一主体；同时实际合成受支持的背景。只有耳机开关与背景可以呈现为会改变此 Composer 输出的选项。其他 Dots 角色设置仍可编辑并写入共享 Prompt，但必须明确标注为组合包不支持渲染的能力。其余四个家族在真实组合包完成前，继续开放 Artwork/Prompt，并将 Composer 标记为不可用。既有项目 JSON 中的历史 `artworkId` 必须仍能恢复对应原始文件。Dots 仍是候选：存在真实 Canvas 只代表组合功能可用，不代表美术已获批准，也不解锁更多 Dots 角色。

**备选方案：**等五个家族的组合包全部完成后再开放 Composer。不采用此方案，因为本次交付要通过一个真实但受限的基准组合包，呈现已经确认的组合创作路径；不支持的家族仍须如实标明不可用。

### 在窄屏采用流动布局并保持清晰的创作顺序

沿用现有 CSS 架构，明确区分宽屏、平板和窄屏布局。在窄屏下，按阅读顺序纵向排列主视觉、家族卡片和创作工作台；无需横向滚动即可看到主要创作操作。必要时可以将编辑器面板改为纵向排列或折叠，但预览及其真实状态标签必须易于找到。遵循键盘焦点和减少动态效果偏好。

**备选方案：**将桌面双栏检查器直接缩小到手机宽度。不采用此方案，因为它会把角色预览和控件挤压到无法使用的首屏中。

## Risks / Trade-offs

- [R01 包含登录和个人空间入口] → 移除这些控件，只保留已经确认的布局与角色方向。
- [五张详细卡片可能把编辑器推到首屏以下] → 精简文案、明确主视觉与卡片的比例，并在主视觉中提供直接的开始创作入口。
- [目前只有 Dots 有受限的新 Composer 组合包] → 使用实际 Canvas 呈现已声明的裸主体/耳机/背景状态；其余四组显示不可用状态，绝不以其他家族素材或生成的整页效果图填补缺口。
- [更改默认作品可能影响现有项目] → 导入旧项目 JSON 时继续解析历史素材 ID 和源文件；仅让新候选成为新建项目的默认素材。
- [视觉工作可能被误认为角色已获批准] → 单独记录界面视觉 QA；五组美术验收和用户确认状态均保持待处理，直到在真实页面上逐组评估。
- [响应式样式可能遮挡现有编辑器控件] → 在桌面、768 px、390 px 和 320 px 真实页面中检查，确保导航、预览、状态和主要操作都能触达。

## Migration Plan

1. 围绕 R01 主视觉、家族概览和创作工作台重组现有页面外壳，同时保留当前项目与状态模块。
2. 两项独立变更准备就绪后，接入家族卡片交互和沉浸式随机入口；确保两项变更仍可分别审阅。
3. 对照真实 Canvas 和已声明的支持范围，验证 Dots 裸主体/耳机/背景组合；验证其他四组 Composer 不可用状态，并确认旧项目 JSON 仍可恢复历史素材 ID/文件。在真实页面中检查 Prompt、导入/导出、参考图流程和首页/工作台导航，并覆盖桌面及要求的响应式宽度。将页面/设计 QA 与逐组美术验收分别记录。
4. 对已获授权的源码发布和站点预览，通过现有私有仓库提交并推送本项目，且只向现有 Site 发布候选版本。回读已保存的版本和部署结果。保留 Site 当前访问策略；发布结果不代表任何角色美术已验收。
5. 如需回滚，恢复到最后一个已知良好的 Git 提交，并恢复同一 Site 上与之对应的先前已保存版本；始终保持项目 JSON 兼容。

## Open Questions

没有会改变视觉方向或要求的未决问题。素材可用性和每个候选的美术验收，均应依据完成后的真实页面评估，并作为各家族的独立决定保留。
