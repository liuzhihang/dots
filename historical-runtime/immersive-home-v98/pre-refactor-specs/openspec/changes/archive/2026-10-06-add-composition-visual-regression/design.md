# Design

## Context

见 [proposal.md](proposal.md) 与 [specs/composition-coverage/spec.md](specs/composition-coverage/spec.md)。本 change 的边界按历史会话中用户从“已经完成了功能的实现”开始的讨论及其后续修正确定；起点之前的旧角色重建方案只作背景。固定五组已调整为可扩展标签；上传、用户自建公共标签和公开发布后置；旧 3D 成品改造已取消。历史助手提出的素材数量与阶段表属于建议，不作为当前库存或交付承诺。

本机 checkout 当前为 `main` / `4d952b907ef4823db7b5e9792726c80a4226eeb8`。静态目录登记 15 个 look；五个基准各有一个额外完整姿态 PNG；Dots 完整配方还区分裸形、耳机 idle 与耳机 classic 状态，其中两个耳机状态引用相同 PNG。按配置状态计数，当前有限目录包含 12 个基准配方状态和 10 个固定完整模板状态，共 22 个状态；对应三种背景形成 66 个模板/背景基线用例。look 身份数、配方状态数、唯一图片文件数和输出用例数是不同的统计口径。

Site 35/cache 83 的 Gallery/工作台确认记录列出 15 个 look，批准范围描述为“PNG模板、背景合成、Prompt”；同一记录的 `supportedStateBoundary` 提到“当前工作台所提供的登记状态”，但没有把姿态 PNG 与具体确认状态逐项映射。因此五个额外姿态的批准覆盖需核定，不能自动宣称逐图通过，也不能把缺少映射解释为用户否决或未批准。素材可用性、内部覆盖状态、人工检查与用户确认必须分开。历史 QA 只对一张莓粉眼镜 Dots 导出做过实际字节核验，不能据此推断全部 PNG 字节或 66 个基线用例均已验收。

2026-10-06 用户截图明确否定当前 Dots 基底 × 头戴耳机模块适配的协调性；根线程将重做该精确适配，现有三张完整确认图保持原样。截图与本地工程可解算结果分开记录：重做适配须逐项检查比例、贴合/接触、遮挡层序、材质/光照、配色，不能因为 Canvas 导出成功而设为通过或继承到新版本；本次模块复核仅用于内部记录，不自动代替用户明确确认。

实施前源码/规范基线仍使用项目包装 v1，并存在纯角色 JSON、旧角色 schema 6–9 或旧别名兼容路径；`verify-creation.mjs` 也含 project v1 和 schema 6–9 的既有 fixture。这些是现状记录，不是目标行为或正向验收承诺。目标合同统一使用 project v2 与角色 VERSION 10，project v1、纯角色 JSON、schema 6–9 和旧别名格式都必须拒绝，且拒绝不得覆盖当前有效作品。角色 VERSION 10 的新项目须通过真实导出、恢复、撤销/重做回归。

`verify-look-gallery.mjs` 覆盖 15 个 look 和五个额外姿态登记；`verify-creation.mjs` 检查角色 schema、配方能力、PNG 注册尺寸/hash/alpha 和部分 Canvas 生命周期。相关 Canvas 与随机测试包含 Fake DOM 或生命周期替身；`verify-preview-capture.mjs` 属于捕获生命周期测试，`verify-assembly-contact.mjs` 检查旧 3D 几何变换并跳过像素。它们不能代替新增 2D 配饰接触的真实像素、浏览器页面或用户美术验收。主线程本轮已运行 `verify-studio.mjs`、`verify-creation.mjs`、`verify-creation-ui.mjs`、`verify-look-gallery.mjs`、`verify-family-navigation.mjs`、`verify-fullscreen-random.mjs` 和 `verify-module-cache.mjs`，均退出码 0；本 change 的规划未重跑这些脚本。没有运行本轮 build、浏览器实测、全量 Canvas PNG 下载或实体设备验收；历史站点回执和批准记录仍是历史版本证据。

## Goals / Non-Goals

**Goals:**

- 建立可重现的当前有限模板基线，以及按能力声明扩展的组合覆盖清单、图鉴和增量影响范围；对声明支持但缺素材或渲染失败的用例保持必检分母。
- 全部有效项目保存、导出、自动保存、恢复、撤销和重做采用 project v2 与角色 VERSION 10；拒绝 project v1、纯角色 JSON、角色 schema 6–9 及旧别名。
- 分开记录素材/资源技术有效性、覆盖执行与问题状态、人工视觉检查和用户美术批准。
- 回读实际原始 PNG、Canvas PNG 与 Prompt；报告提供真实分母、执行数和硬约束排除原因。
- 保持已批准模板资产不变，保持首页布局、群像、卡片、导航和文案不变；标签界面位于图库和工作台。

**Non-Goals:**

- 本 change 不新增或删除角色素材，不承诺一次完成 24 个基础设计或中期约 70 个素材建议；不得因格式移除删除已批准 PNG。
- 不实现旧 project v1、纯角色 JSON、角色 schema 6–9 或旧别名的迁移/兼容。
- 不改变首页现有搜索、`homeFamilies` 五组场景、群像、卡片、导航和文案；不把标签筛选 UI 放入首页。既有卡片可以通过内部路由携带 Gallery 标签查询条件，但首页展示保持原样。项目菜单只移除旧角色 JSON 导出项 `save-character`，保留 v2 项目导出、菜单容器和其余功能。
- 不实现用户上传、自由公共标签、公开发布、账号、存储或审核系统。
- 不重新启动已取消的 3D 成品改造，不把旧 3D 结构诊断或几何测试当成 2D 像素证据。
- 不生成全部笛卡尔积图片、不以截图差异自动接受视觉基准、不发布站点。

## Decisions

### 1. 用统一用例目录表达输入、资源与证据

覆盖用例按稳定身份组织，最少关联 look 或基底、配方状态、素材 ID/版本/hash、姿态、视角、背景、组合配置和渲染输出。唯一图片文件的字节检查可以去重，但不同可编辑状态仍各自占一个配方用例。当前模板基线按 22 个配方状态与三种背景生成 66 个输出用例。报告分开记录声明应检验分母、明确硬约束排除、实际可解算数和已执行 pass/fail/blocked；只有合同明确不支持或互斥等硬约束可排除。合同声明支持但缺素材、来源/版本/hash 或尺寸不符、解算或渲染失败的用例留在分母并标记 fail/blocked；存在活动兼容声明时不能以空分母报通过。人工批准范围缺少状态到素材映射时另记“确认范围待核定”，不得推断通过或否决。

**替代方案：** 用截图文件名或 seed 作为唯一身份。它们不能稳定指出素材版本或完整配置；seed 也不能保证后续版本仍抽到同一素材，因此不适合作为回归用例主键。

### 2. 先全量当前有限路径，再按兼容图分层扩展

第一批基线逐项覆盖当前 15 个 look、22 个登记配方状态、66 个状态/背景输出用例和所有适用真实导出。扩展组合由素材声明的基底、姿态、槽位、依赖、互斥和邻接关系生成：单素材对声明支持基底/姿态全量；一般兼容关系覆盖所有有效 pairwise；高风险接触链路做定向三/四因素覆盖；精选批准配方全回归；大空间使用固定 seed 与性质检查，并检查参数代表值及边界。只有合同明确不支持或互斥的组合从应检分母排除；符合支持声明但执行失败的仍留在分母并计 fail/blocked。

实施顺序把“before 基线”和“首个基础报告”分开。用例盘点、Prompt 回读方法、source/resource 清单与批准映射可先准备；实现前的早期 PNG/Prompt 捕获只描述旧实现，MUST NOT 计作新行为通过。待 `evolve-catalog-tags` 的目录/页面切片和 `add-modular-2d-composition` 的 v2/VERSION 10、模板 adapter 与导入接口代码可调用后，执行 group 1 的最终集成检查。stage2 模板入口与共享 API 已接线即可开始联测；不要求 stage2 依赖本报告的验收 checkbox 先勾选。stage2 模板输出验收与本 change 的 tasks 1.4–1.10 使用同一冻结 source ID/resource version；task 1.11 执行唯一一次 22×3=66 输出捕获并汇总、交付首个基础模板报告。stage2 与本 change 复用这份捕获，避免交叉等待；tasks 1.2、1.3、1.7 的 before 证据只作旧实现对照。stage3 只等待该报告，不反向阻塞它。报告只要求现有模板、v2 项目基础、旧格式拒绝、Prompt 与实际导出；尚未接线的模块真实适配和随机池范围记 deferred/blocked，不计 pass，但不阻止模板基础报告交付。组合图鉴基础可并行建设；stage2 在接口可用后消费，不要求本 change 等待全部模块素材、stage2 全部结束或 stage3 完成。

**替代方案：** 预渲染全部笛卡尔积，或只靠随机截图。前者空间增长失控，后者无法说明覆盖分母，也可能漏掉高风险接触关系。

### 3. 组合图鉴复用同一用例目录且按需分页

内部图鉴以基底、素材、姿态和视角筛选分页；单格连接到完整配置与资源版本，问题按穿插、悬空、遮脸、比例、风格、画布和导出分类。它消费覆盖用例而不建立第二套组合规则，页面按需捕获，不预生成整个组合空间。自动像素差异和图鉴内审只写内部状态；用户批准只能来自明确绑定版本、状态范围和素材映射的人工确认。若历史批准只有宽泛状态边界而无可核对映射，界面标为“确认范围待核定”，并保留原记录。

**替代方案：** 为每张截图建立独立手工备注表。该方式容易与用例配置、素材版本和增量影响关系失配。

### 4. 依据素材依赖和变更类型计算增量回归

影响图记录基底、槽位、姿态与相邻素材。新增素材触发其声明的所有基底/姿态和邻接关系；公共布局、Canvas 合成、染色或基底变化扩大到所有相关用例；标签浏览变化检查 Gallery/Workbench 过滤与默认随机候选池；主题组合规则变化检查受影响主题配方与高风险邻接。覆盖基础设施随 `add-modular-2d-composition` 同步建设，无需等待全部素材完工。

老虎机仍由 `upgrade-randomizer-to-rendered-recipes` 将默认候选接到真实可渲染配方。本 change 可先覆盖当前模板；随机池专属增量回归只有在该候选池接线完成后才可执行并报告，不得提前标为已完成。

### 5. 冻结结果固定环境并写入新证据目录

每份报告固定源码提交、cache/module 版本、source ID 和源码清单/hash、浏览器和视口、画布尺寸、素材版本/hash、完整配置、seed 和静态帧参数，并记录原始图像、Canvas 导出与 Prompt 回读结果。若工作树未提交或 source ID 未覆盖该树，还固定 dirty-source snapshot hash 和变更路径/文件 hash 清单；commit 与 cache 版本本身不足以绑定脏工作树。新冻结目录使用 `design/acceptance/current-<本机日期>-v<cache版本>/`；目录已存在时换用新的唯一目录，不覆盖任何当前或归档证据。截图比较只产生待审查差异，不自动接受新基准。

### 6. 按上游合同验证统一 project v2 与 null-or-resolved 组合引用

所有新保存、自动保存、导出、恢复、撤销和重做的有效项目统一采用 `{format:"dot-studio-project",version:2}` 包装及角色 VERSION 10。`creation.composition` MUST 显式为 `null` 或完整的已解算引用：Prompt-only/未解算编辑态保留完整角色配置但将其设为 null；已渲染模板/模块作品 MUST 提供 `kind: template|modular`，保存目录版本、实际素材稳定 ID/版本/hash、配方 ID/版本、标准化配置及解析指纹，模板还保存实际模板/状态 PNG 引用，模块组合保存基底和按槽位排序的素材引用。模板随机应用和默认随机成品必须有非 null 的已解算引用；null 配置不得进入默认成品池。导入依据本地登记资产重新解算，JSON 不得提供任意图片、路径、URL、图层清单或可信的直接 `ResolvedComposition`。

旧格式移除合同由上游 change 持有。本 change 只验收 project v1、纯角色 JSON、角色 schema 6–9 与旧角色别名被拒绝，拒绝时保留当前作品；不对迁移或兼容作正向承诺。实施前源码存在的旧读取路径只作为现状说明。已批准模板文件及历史冻结记录保留，标签目录仍是维护者内置目录数据，不写入项目 JSON。

### 7. 首页呈现保持不变，标签筛选在 Gallery/Workbench

首页现有搜索、`homeFamilies` 五组场景、布局、群像、卡片、导航和文案保持当前设计。标签检索控件位于 Gallery/Workbench 内容区；已有首页卡片可以使用原展示内容并通过内部路由携带相应 Gallery 标签过滤条件，不新增首页标签模块或重新绘制群像。项目菜单移除旧角色 JSON 导出项 `save-character`，保留统一 v2 项目导出、菜单容器和其他功能；浏览器验收将此项记录为预期功能差异。浏览器回归固定现有首页视觉，并验证既有全局随机入口仍能打开和使用；随机内容验证按其实际接线状态报告，不将 Prompt-only 候选称为渲染结果。

### 8. 模块适配复核绑定精确版本并单独导出

协调性复核以基底/组件资源版本与哈希、几何 fitPolicy/profile/sourceParts、配方版本与指纹、姿态和视角构成的 subject 为键。一个 recipe 可含多个动态组件，但每个组件的资源引用、fitPolicy、sourceParts、适用 profile 与 fitVersion/fingerprint/已解算部件必须分开保存；只有 resolver 明确提供时才记录 recipe 级聚合指纹。唯一基础设计、组件×基底/姿态适配、可解算配方和背景输出分别计数，不将五个共存配方误报成五个素材或五个单组件适配。五个检查维度初始均为 `unreviewed`；整体结论初始 `pending`，只有五项全为 `pass` 才能选择 `ready-for-explicit-confirmation`，拒绝需要原因。新版本不能复用旧 sidecar。图鉴导出时，捕获清单和冻结报告需保留单格 localStorage 问题标注与精确复核记录；工程覆盖、协调性复核和美术批准是互不替代的结果，复核状态不改变工程分母或默认候选资格。首批动态适配只按可信目录真实声明的基底、姿态与配方生成用例；不预设 recipe/输出总数，不推断任意角度或任意姿态支持。每份实际 Canvas 输出需附带 resolver 给出的 fit/profile、实际图层变换、层序、遮挡和逐组件指纹元数据，便于对比 PNG，但这些元数据不构成美术批准。

## Risks / Trade-offs

- **有效组合数量仍可能快速增加** → 使用声明能力排除明确不支持或互斥的输入，完整覆盖单素材适配、有效 pairwise、明示的高风险组和批准配方；其余大空间固定 seed 并公开实际分母。
- **资源声明与真实页面结果可能不一致** → 把资源缺失、渲染错误和视觉问题分别记录；运行期候选能力不能取代真实浏览器画面检查。
- **旧项目将无法直接导入** → 这是用户明确选择的断代合同；v1、纯角色 JSON、schema 6–9 和旧别名显示拒绝原因并保留当前有效作品，用户需重新创建 project v2。系统不得暗中迁移。Prompt-only 编辑态仍可用 v2 + `composition: null` 保存和恢复角色设定。
- **历史批准范围无法逐文件核定** → 15 个 look 保留确认记录明确列出的身份；`supportedStateBoundary` 对额外姿态的覆盖须核实原页面和素材映射，核定前标记“确认范围待核定”，既不推断逐图通过也不解释为用户否决。
- **内部视觉比较可能被误读为用户批准** → 报告分开保存自动/工程状态、人工问题记录和用户明确批准；禁止自动更新基准。
- **图鉴全量生成会耗时或占用空间** → 只按筛选与页码按需捕获，并保留完整可复现配置供单格回开。
- **首页路由携带标签条件可能影响当前编辑作品** → 标签只改变 Gallery 结果范围；不得自动载入或覆盖工作台角色，只有明确选择“用这个形象定制”才替换活动作品。
- **未访问当前部署或设备导致证据边界有限** → 本 change 不声称当前线上页面、全部导出或实体手机已经通过；实现后仍按固定本地页面实测并分别记录线上/设备范围。

## Migration Plan

1. 先盘点用例、准备 Prompt 读回、source/resource manifest 和 approval mapping；可额外捕获旧实现作为 before 对照，不能记作通过。
2. 待 `evolve-catalog-tags` 的目录与页面切片、`add-modular-2d-composition` 的 v2/VERSION 10 和当前模板/导入 API 已可调用后，完成模板 v2、Prompt-only null、旧格式拒绝及页面/菜单回归。验收以实现和 API 已就绪为门槛，不等待对方依赖本报告的 acceptance checkbox。
