# Design

## Context

源码和 `dist/assets/` 目前登记 15 个完整图库 PNG 模板；5 个额外静态姿态/表情 PNG 也是完整画面，Dots 另有裸形与头戴耳机的完整图像/配方切换。当前没有可自由组合的独立角色或配饰 PNG，也没有独立的配色/材质组件变体。`atelier/` 中两张旧整图和 `qa/` 中三张几何测试遮罩都不是可组合角色素材。10 个非基准 look 使用固定整图，只参与背景合成。

v83 美术确认记录列出了 15 个登记 look，并将 `supportedStateBoundary` 定义为当前工作台提供的登记状态。5 张附加姿态 PNG 没有逐文件独立列出；实施前需核定这些文件是否落在既有确认范围内，不能据此断言已排除，也不能把确认自动扩展到新的组件适配。代码里的 `unreviewed` 与等待确认文案同样不能覆盖冻结记录。确认记录保持原样，当前有效状态按具体证据解析。项目的版本化验收合同见 `openspec/specs/character-visual-acceptance/spec.md`。

染色路径存在一个可复现的内存问题：合成器把带有 `colors.body` 染色路径的合成测试包判为 `available`，即使输入为 `#FF0000`，`resolveCompositionConfig()` 返回的仍是基底色 `#3264FA`。现有内置包没有登记 `tintPath`，因此这是新模块素材启用染色前必须修复并验证的潜在缺陷。任何颜色能力都要先核实解析值，再检查实际绘制像素。

当前项目包装为 v1，角色 schema 为 VERSION 10。`fixed-image-2d` 与 `layered-2d` 要求完整 PNG 源、精确可信配方和登记的本地资产。旧 Three.js/WebGL/CPU 渲染器仍只用于结构诊断。

## Goals / Non-Goals

**Goals:**

- 新增版本化的 2D 素材契约和确定性共享解算器，供模板适配、模块编辑、精选方案、随机结果、项目恢复、预览和导出共用。
- 兼容性由明确的基底/布局、姿态、槽位、挂载、接触和渲染能力决定，不由浏览标签推断。
- 所有新保存、导出和随机应用结果统一使用包装 v2；实际可绘制的模板与模块结果按素材 ID、版本、哈希及配方复现，Prompt-only 参数保持可保存，且不伪造解析引用或写入任意图层清单。
- 保留当前确认的 15 个 look、现有完整 PNG 模板与背景合成、已登记状态、撤销/重做、当前活动会话草稿、角色 VERSION 10 和结构诊断边界。
- 新标签与素材编辑 UI 放在图库和工作台；网站首页布局、群像、卡片、导航与文案保持不变。
- 为后续组合图鉴与增量视觉验收提供稳定素材、适配、批准和解析指纹数据。

**Non-Goals:**

- 不把现有完整 PNG 拆切或改作模块配件。
- 不实现用户上传、账号、公开投稿、审核、云存储、任意视角、任意姿态、连续动画或正式 3D 成品。
- 不迁移前端框架，也不重做已确认的美术。
- 不承诺一次交付完整 24 款首批设计；按审阅过的批次扩充。
- 不迁移旧项目格式或旧字段别名；旧包装、纯角色 JSON 与旧角色 schema 只显示不支持提示，不自动迁移。
- 不改版首页，也不把新增标签或素材控件放到首页。

## Decisions

### 标签与身份目录保持分离

新部件和配方登记在维护者管理的本地目录中，并具有稳定 ID。每条素材记录 SHALL 包含独立版本和 SHA-256、类别与占用槽位、允许的基底/布局 ID、风格适配、支持的姿态与视角、挂载/对齐规则、依赖与互斥、图层顺序与遮挡方式、抓握/接触要求、可染色区域、来源和使用范围、工程渲染状态、发布资格及美术批准引用。

新 v2 项目通过当前登记的 Look、素材与配方身份建立引用；不得从旧格式的别名或恢复副本自动转换出标签、素材或适配能力。角色 VERSION 10 中当前 `family` 身份字段仍按现行含义保留，不全局改名为 tag。Look 与标签的关系只负责发现和组织内容；标签 MUST NOT 赋予几何、姿态、材质或渲染能力。角色身份、美术风格、身体/布局适配、表情、姿态、手/抓握素材和道具挂载分别建模。图库/工作台查询可消费 `evolve-catalog-tags` 的分类结果，但模板身份与模块素材使用各自稳定 ID，TagQuery 仅决定发现范围；共享 resolver 的硬兼容只由素材合同和选定基底决定，因此 v2/模板基础不等待标签 UI。

### 先解算完整候选，再揭晓或绘制

新增确定性的共享解算器，输入可信基底、用户配置、选定模块 ID 和目录版本，先检查硬兼容约束，再应用软推荐规则，并返回不可变的 `ResolvedComposition`。解析结果 SHALL 以素材 ID、版本和哈希标识有序图层、登记变换/锚点、裁切与遮挡规则、姿态/抓握配方、标准化输入，以及输入和解析指纹。

硬约束决定组合能否绘制，包括精确基底/布局、槽位占用、姿态/视角、依赖、互斥、有效锚点、抓握要求和已核验素材。冲突时拒绝组合并给出可理解的原因；锁定选择不能静默替换。软规则只调整可行组合的美术推荐排序；用户显式进入高级编辑后可以放宽推荐，但不能令不兼容素材变得可渲染。

手动编辑、精选组合、随机候选、项目恢复、预览和导出共用同一个解算器。模板适配器将已有 `fixed-image-2d` 和 `layered-2d` 输入接入同一结果接口，同时保持旧配方现有的精确图层选择与校验。旧 `layer.when` 拒绝规则和完整结构配方检查保持不变；`modular-2d` 是独立版本化类型，不能作为旧包格式错误时的宽松回退。

### 默认随机候选保持稀疏且完整可绘制

随机流程 SHALL 在动画开始前，从兼容、哈希已核验、工程可用的素材和完整配方生成有限候选。缺少完整渲染能力的候选必须先被排除。默认排序 SHALL 倾向至多一件主配饰、一件辅助配饰和一件主要道具；基底固有穿搭不计入数量。这是默认搭配策略，不要求填满所有槽位。显式锁定保持不变，兼容池为空时给出具体说明。

首轮正面静态验证建议使用 Dots 几何基底、栗发人物基底和柴犬基底。首批小范围素材可评估高质量耳机、圆框眼镜、围巾和杯子，但只在各自实际声明支持的基底与姿态上登记。这是建议默认值，不表示所有素材都适配三个基底。24 款基础设计分批评审和扩展；此前约 70 款的估算不是交付承诺。

候选提供 API 与随机器界面分层：tasks 2.4 首先只从可信模板 adapter 暴露可绘制且具有有效确认资格的现有模板结果，使随机 change 能先完成真实模板候选与展示；tasks 4.4 再把实际制作、登记且逐适配获批的模块结果追加到同一 API。阶段 1 的 v2/template 格式、task 2.4 的候选接口及 stage4 当前模板捕获基础足以启动模板随机，不依赖 task group 3 的新素材。

### 所有新项目统一使用包装 v2

所有新保存、导出和随机应用结果 MUST 使用 `{format:"dot-studio-project", version:2}` 与角色 VERSION 10。`creation.composition` MUST 是 `null` 或共享 resolver 实际生成的可信 `ResolvedComposition` 引用对象；非 null 对象以 `kind` 区分 `template` 与 `modular`。模板引用保存完整模板/状态 PNG 的稳定素材 ID、版本、哈希和配方引用；模块引用保存基底、输入素材、配方和槽位引用；两者均保存目录版本、姿态/抓握与标准化输入、输入指纹和解析结果指纹。角色 VERSION 10 字段中超出真实 Canvas 能力的设置仍可作为 Prompt-only 值保留；若完整模板本身可真实绘制，composition 只代表该实际模板，不代表不支持的附加设置。没有实际 Canvas 输出时 `creation.composition` MUST 为 null；不得创建虚假的素材引用、图层或解析指纹，也不得阻止保存 Prompt 设定。不能渲染的原因从角色配置和 resolver 重新计算，不作为可信项目事实持久化。默认随机只接受非 null 且完整可绘制的 composition。

项目 JSON MUST NOT 携带图片字节、可执行图层路径、任意 URL，或把导入 JSON 自带的 `ResolvedComposition` 图层清单当作可信权威。仅接受包装 v2 且角色 VERSION 10 的项目；导入时若 composition 非 null，则按 kind 从本地可信目录解析登记 ID、版本和哈希，校验约束并重算结果；若为 null，则恢复白名单内的 Prompt-only 角色配置，并从当前 resolver 重新计算能力与冲突说明。缺失、哈希不符或不兼容时，显示具体错误，不能静默替换。旧包装、裸角色 JSON（包括裸 VERSION 10）、VERSION 10 之前的角色 schema 和旧字段别名输入明确提示当前格式不支持；不自动迁移、不转换别名、不声称数据已删除，并保留原始导入内容/旧存储草稿不被覆盖。当前会话中的有效草稿按 v2 保存，并在编辑、自动保存、撤销和重做中保持一致。VERSION 10 包装也 MUST NOT 接受 `legacy.originalConfig` 或 Muse/Pets alias 字段作为绕行迁移入口；当前 `family` 字段仍按角色 v10 合同解释，不全局改名为 tag。超出 Canvas 能力的参数可作为 Prompt-only 值保存在角色 VERSION 10 中，不能为了导出伪造解析引用、静默替换角色或阻止保存角色配置。

### 将美术批准作为独立的适配门槛

工程可用只表示本地素材存在、哈希匹配、约束可解且 Canvas 能绘制，不等于适配协调性通过或用户美术批准。准备进入精选或默认随机池的每个基底 × 素材 × 已声明姿态/视角适配，SHALL 有独立的精确绑定批准记录：基底资源 ID/版本/hash、组件 ID/版本/hash、配方 ID/版本、姿态/视角和规范化配方指纹。指纹覆盖布局、风格、放置锚点与尺寸、图层顺序及高风险适配声明；任何绘制相关变化，即使漏升版本，也使批准失效。多组件 recipe 必须审核完整组装结果，且其中每项素材的批准记录都要绑定该组合 recipe，不能用单件适配页面或另一组件的批准补足。证据记录冻结来源清单路径与来源 SHA-256，并逐页记录页面路径、页面 SHA-256 和视口尺寸。适配记录另有五项人工 `coordinationChecklist`：比例（`proportion`）、接触（`contact`）、遮挡（`occlusion`）、材质与光照（`materialLighting`）、配色（`palette`）；每项须根据所绑定的真实页面明确标为 `pass`。缺项、`issue` 或 `unreviewed` 均保持待处理，不进入精选或默认随机。该清单不自动计算，不替代工程硬约束，也不替代独立的用户美术批准；工程可绘制且五项通过后，仍需针对该适配取得用户确认。未批准素材可以显示为明确标注的预览候选，但不得加入精选或默认随机池。v83 确认按记录的模板/登记状态边界解释，不能延伸为新组件组合或新适配的确认。

该 change 会暴露素材 ID、哈希、来源/使用范围、兼容关系和解析指纹，供组合视觉回归 change 生成全量与增量覆盖。捕获设施可以并行建设，但不能代替人工美术批准。

### 分类、接触配方与扩展批次

素材类别与占用槽位分开：目录可扩展到帽子、发箍/发饰、耳机、眼镜、内搭、外套、下装、连体服装、颈饰、腕饰、鞋、包袋、手持/使用道具、牌面及动物专属穿戴；一项设计可以占多个前后层/接触槽位，前台六个揭晓阶段不限制底层分类数量。指示牌拆为牌面资产、挂载方式和文字输入，不统一塞入头饰。表情、手势/抓握、身体姿态、连续动画、Agent状态分别记录；本期只开放有静态配方的部分。

帽子需要对应帽下发型/头部适配，耳机分前后遮挡且保留连续头梁；颈饰、金链、袖口与腕饰必须声明共存和层序。外套、手表和鞋只对有相应躯干/手腕/脚结构的基底声明能力。杯子、书、电脑使用具体抓握/接触配方，使姿态、手部/前爪与视线共同成立，不用通用手掌任意持物。角色自身明暗和配饰接触层次保留，独立脚底椭圆阴影团不进入新资产；旧成图如发现同类问题需另记窄范围修正，不在本方案中批量重做。

### 每个组件按实际基底几何动态适配

“动态适配”必须由素材局部锚点与维护者标注的基底 geometry 推导。耳机登记带版本/哈希的 kit，并将 `band`、`leftCup`、`rightCup` 作为不重叠的 `sourceParts` 矩形；不从完整角色图裁切，也不改变完整基底像素。版本化的 `resolveHeadphoneFit` 根据真实 profile 的头顶、左右耳挂、连接锚点和面部 keepout 推导杯体与连续头梁的位置、尺寸、朝向、遮挡和层序。

眼镜与围巾同样使用动态合同，不登记每个 look 的固定 placement：`resolveAnchorPairFit` 根据维护者为人形 classic 标注的瞳孔双锚和为柴犬 classic 标注的颈部接触双锚，计算源组件的平移、角度与等比缩放。双锚适配不额外声明任意姿势、视角或物种；缺失、越界或冲突时拒绝整个组合。透明 halo、比例、接触、遮挡、材质光照与配色仍须通过人工协调性检查，算法可解不表示组件看起来协调或已获得用户批准。

每个受支持姿态的 `baseGeometryProfile` 精确绑定 `baseId`、完整基底 asset refs、`bodyId`、布局/风格、姿态、视角和画布尺寸，并记录该 fit 类型需要的归一化特征点。标签与 family 不提供几何。组件契约包含版本化 `fitPolicy` 与对应素材哈希下的 `sourceParts`。共享 resolver 对同一 recipe 中的每个动态组件分别运行适配器并验证其依赖、槽位、互斥、profile、尺寸、接触和遮挡；`ResolvedComposition.inputs.fitRefs` 按 asset ID 稳定排序，每条引用保存组件 fit 版本、指纹与 profile 引用，项目另保存整组 fit 聚合指纹，各 render module 保留自己的部件变换和 fingerprint。Canvas 按 `(module.z, part.z)` 绘制。只有目录明确登记的 recipe 才能组合多件素材；不能从各自单独可用自动推导交叉组合。

cache 85 是初始试点基线：Dots 裸形、栗发人物 classic 与柴犬 classic 三个状态，四项单件适配和一条明确的人形耳机+眼镜 recipe，共五条基线 recipe。用户随后授权将同一个耳机 kit 扩展到全部四个已登记人形状态。完成矩阵目标是耳机×Dots、耳机×四个人形状态、眼镜×人形 classic、围巾×柴犬共七项单件适配，并保留一条仅绑定人形 classic 的显式耳机+眼镜组合 recipe，即 8 条目标 recipe。它是规划覆盖范围，不是当前可用目录清单：实现前根需从当前源码核实各条 recipe 的登记/工程状态，未通过真实 Canvas/PNG 检查的行不得计入可用库存或默认池。若任一 solver 的硬约束失败，不登记该适配或拒绝整个组合；不能静默掉件或退回固定坐标。对同一组件/同背景更换真实几何 profile 的测试应产生不同变换、fingerprint 和可检查的 Canvas/透明 PNG 像素，不以只改背景证明动态能力。工程可绘制、人工协调性 checklist 与用户美术批准分别记录，不重启 3D 动画范围。

### 2026-10-06 当前人形耳机适配反馈

用户明确否决 cache 85 的“人物+耳机”与“人物+耳机+眼镜”两条协调性结果。精确反馈、附件哈希、recipe/version、组件 hash、基底引用及 geometry profile fingerprint 记录在 [`human-headphone-feedback-20261006.json`](../../../../design/modular-pilot-20261006/human-headphone-feedback-20261006.json)，原始参考图的副本也保存在同目录。该决定只适用于 source `sha256:9bcd516a91b2d366f1921073962909ee801b9bf75d765c83c2bdc1b200daa672` 下绑定的两条当前配方；Dots 耳机、人形单独眼镜、柴犬围巾和整页都仍是未批准，不把拒绝外推到它们。

这两条配方返工时，耳机 geometry fit 必须同时参考人形的耳廓/挂点与头部几何来求耳罩尺寸，不能只用固定头宽比例；头梁需沿头顶弧面贴合；profile/遮挡合同需能表达发丝与耳朵的前后关系，使头梁和耳罩按正确深度穿过/覆盖头发、耳朵。材质与接触阴影需要与人形头发、皮肤及绒布耳罩视觉一致。应以新 profile/policy/recipe 指纹和新 Canvas/PNG 证据复查；如果当前扁平基底无法可靠表达所需几何或遮挡，就将人形耳机及其多组件 recipe 标为 unsupported，不复用 cache 85 输出或旧 profile fingerprint。

## Risks / Trade-offs

- [Risk] 每个基底和姿态都需要分别记录兼容适配，记录数量会增长 → 只登记明确支持的稀疏适配，并按声明范围生成检查，不声称笛卡尔积已全覆盖。
- [Risk] 解算器或项目导入接受过期或被替换的素材 → 只从本地目录解析 ID，校验保存的哈希，重新计算指纹，并拒绝静默替换。
- [Risk] 软推荐被误当成渲染约束 → 分开返回硬兼容结论和排序结果，并明确标示高级编辑操作。
- [Risk] 染色元数据声明了 Canvas 实际没有绘制的效果 → 只有解析结果保留颜色且像素级检查证明重染后，才标记为可渲染。
- [Risk] 新素材使用了版权或授权范围不清的来源 → 每件素材记录来源和使用范围；人物与动物保持原创，拒绝把无分发授权的参考图像像素做成可发布组件。
- [Trade-off] 旧存储和旧导入格式不再自动迁移 → 对旧包装、纯角色 JSON、旧 schema 与别名显示 unsupported，原始内容不被覆盖且不声称已删除；新版本只读写 v2。

## Migration Plan

实施按可独立交付的任务切片推进，不把整项 change 作为单一前置条件：

1. **现有模板与项目格式基础（tasks 1.1–1.6）**：为当前 15 个 look 和 22 个登记配方状态建立可信模板引用；用现有完整 PNG 经模板 adapter 生成真实 `kind: template` 引用，并让无法绘制的 Prompt-only 编辑态使用 `composition: null`。所有新读写、导出、自动保存、当前会话草稿、撤销和重做统一为包装 v2/角色 VERSION 10；删除旧格式 reader、迁移恢复路径及 `save-character` 菜单项。该切片只用现有模板与 Prompt-only 输入，不等待新组件 PNG 或真实随机器。
2. **模块合同与可复用候选接口（tasks 2.1–2.5）**：在模板 API 上增加独立版本的模块目录、硬约束解算分支、染色字段修复、候选提供接口，以及版本化头戴和双锚 fit solver。任务 2.4 仅依赖第 1 组模板基础及所需目录查询，可先于模块扩展独立交付；初期只返回经核验且具备有效确认资格的现有模板 `ResolvedComposition`。逐组件 fit、按 ID 排序的 `fitRefs`、聚合 fingerprint 和模块/部件层序进入同一可信 resolver，不由随机或 UI 单独实现。
3. **标签与当前模板捕获并行**：标签 UI/query 仅依赖 `evolve-catalog-tags` 的 Look—Tag 目录和 `TagQuery` 任务 1.3–1.4；不等待整个 change。`add-composition-visual-regression` 可并行完成改动前的模板清单、实际 PNG/Canvas 和 Prompt 回读（其任务 1.1–1.3）。当本 change 的 1.1–1.5 及 1.6 接线/API 可用后执行 v2、旧格式拒绝和页面检查；本项 1.6 与视觉回归 1.11 以同一最终源码/资源版本的 66 项捕获联合验收，复用一次证据，不等待对方依赖该报告的验收任务先勾选。改动前捕获不能冒充改动后的通过证据。
4. **真实模板随机先行**：当本 change tasks 1.1–1.6、2.4 以及 stage4 当前模板捕获基础交付后，`upgrade-randomizer-to-rendered-recipes` 可以消费已登记模板候选，验证真实模板随机，不等待 tasks 3 的新素材。
5. **模块素材与工作台能力**：按 tasks 3.1–3.4 分批制作/登记初始四项单组件适配及一条明确的人形耳机+眼镜 recipe，并按新增授权将耳机单件适配覆盖四个人形状态（新增 wave、黄色卫衣丸子头、金发眼镜三个目标 recipe）。耳机使用同一个弧线 fit solver 和同一 kit，但每个人形状态有独立 profile、recipe 绑定和真实输出；眼镜/围巾按各自双锚动态 fit。任一 geometry profile 无法通过硬条件，明确拒绝对应 recipe。随后按 tasks 4.1–4.4 接入模块 UI、模块 v2 引用及各入口的共享 resolver。所有新/修订适配仍须分别通过工程检查、协调性检查和用户美术批准，未批准项不进入精选或默认随机。
6. **增量覆盖与交付**：按 tasks 5.1–5.5 接入 stage4 的组合覆盖/图鉴设施，验证影响范围、浏览器页面和实际 Canvas/透明 PNG。cache 85 的历史基线是四项单件适配和一条多组件 recipe；计划目标扩展为 7 项单件适配、8 条 recipe。实际覆盖数必须从当前源码中已登记且可解的完整配方动态计算；规划数量不是当前库存或已验收数。旧 v84 报告只作基线证据，新增/修订的人形状态须由新冻结捕获记录。新增 recipe 不等于新增基础设计或批准；截图保持待审，待真实页面与用户逐项决定后交付审阅，不在此 change 发布站点。

回滚时关闭模块目录入口并恢复现有模板使用。v2 项目原样保留；不得把 v2 组合降级、剥离 ID 或伪装成旧格式。当前模板、背景合成、会话草稿和撤销/重做不因模块功能回滚而删除。本 change 不包含 Site 部署。
